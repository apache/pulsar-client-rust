# 8. Quality

> Previous: [7. Public API](7-api.md).

## 1. Observability

**Logs** go through `tracing`. Spans carry the identifiers that tie events together: the topic, the producer or
consumer name, the subscription, and the connection's addresses. Segment ids appear in logs only, never in the
API.

**Metrics** are recorded through [nanometer](https://github.com/merlimat/nanometer): each loop has its own local
handles, so recording costs no synchronization, and the exporter sums them. The application passes an
OpenTelemetry `MeterProvider`, and the client depends only on the `opentelemetry` API crate. Metric names and
attributes are the Java client's, so dashboards work for both. The Java instrumentation in `pulsar-client`
defines, among others:

- `pulsar.client.connection.opened`, `.closed` and `.failed`;
- `pulsar.client.lookup.duration`;
- `pulsar.client.producer.message.send.duration`, `pulsar.client.producer.message.pending.count`;
- `pulsar.client.consumer.message.received.count`, `pulsar.client.consumer.message.ack`;
- `pulsar.client.memory.buffer.usage`.

The full list is taken from the Java sources when metrics are implemented. Metrics of state that spans loops,
such as the client memory buffer, use nanometer's shared gauges.

## 2. Testing

| Layer | What it covers | How |
|---|---|---|
| Unit | Routing, layout application, the producer barrier, position vectors, ack tracking, batching and bucketing, MessageId and Checkpoint encoding. | Plain tests on the state machines ([2](2-architecture.md) §2). |
| Simulated broker | Protocol flows and failures: handshakes, lookups and redirects, splits and merges in the middle of produce and consume, reassignments, mode flips, reconnects, timeouts. | `apache-pulsar-testkit`: a scripted broker built on the protocol crate's codec, over in-memory connections, on a controlled clock. Deterministic, with no sockets or sleeps. |
| Integration | The client against a real broker. | The released `apachepulsar/pulsar` image (5.0.1 today), started by the test harness. A broker built from master (`./gradlew docker`) when a test needs an unreleased change. |
| Cross-language | Same routing, and identifiers that move between SDKs. | Routing vectors and golden MessageId and Checkpoint bytes generated by the Java client, plus Java ⇄ Rust produce and consume tests. |

### 2.1 Porting the Java tests

The scenarios of the Java V5 tests are ported, not their code:

- `pulsar-client-v5/src/test`: about 190 tests, mostly unit tests over Java internals with mocks. They map to
  unit and simulated-broker tests.
- About 500 tests elsewhere in `apache/pulsar` use the V5 API, mostly the `V5*Test` and `ScalableTopic*Test`
  classes in `pulsar-broker`. They map to integration tests.
- The Pulsar Functions, proxy and SASL tests are out of scope.

`tests/PORTING.md` will list each Java test class with its Rust counterpart and status, so coverage can be
tracked. Many broker tests trigger splits and merges, or look at broker state. Against a container, that needs
the admin REST API, so the test harness gets a small admin client of its own ([1](1-scope.md) §5).

### 2.2 Conformance

The spec's test guidance (*conformance* §5) becomes a named suite: routing vectors, a split or merge during
active produce and consume, a broker failover, cumulative ack across segments, and checkpoint round trips across
a layout change. It is written so that it could later grow into a suite every SDK runs.

## 3. Compatibility and versioning

- **Crate versions:** 0.x until the API settles. 1.0 once the required core is complete and the API has been
  used in practice.
- **Spec version:** each release states the spec version it conforms to (1.0 to start), and which optional
  capabilities it implements.
- **Brokers:** Pulsar 5.0 or later ([1](1-scope.md) §3).
- **Serialized identifiers:** MessageId and Checkpoint bytes stay readable by every later release
  (*stability* §4.3). The golden-byte tests guard that.

## 4. CI

- Linux on io_uring, and Linux forced onto the polling driver, so that the fallback stays tested.
- macOS.
- Windows, build only at first.
- `rustfmt`, `clippy` (with `await_holding_refcell_ref` denied), docs, and the minimum Rust version.
- `cargo-deny` for licenses (ASF third-party policy) and advisories.
- Integration tests against the broker container.

## 5. Releases

Releases follow the ASF process: a signed source release, a vote on dev@, and then publishing to crates.io from
the voted source. Every source file carries the ASF license header, and the repository has `LICENSE` and
`NOTICE` files.

## 6. Performance

A benchmark harness measures throughput and latency for produce and consume, at different payload sizes, loop
counts and segment counts. It compares the client with the Java client and pulsar-rs on the same broker. An
OpenMessaging Benchmark driver can follow once the API is stable.
